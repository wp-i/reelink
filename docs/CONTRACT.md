# Internal implementation contract

Reelink: Windows-only Tauri 2 + React/TypeScript. All UI Chinese. Local first.

Frontend invokes these Tauri commands (camelCase argument keys):

- `decode_clipboard() -> QrResult`
- `decode_image({ data: number[] }) -> QrResult` (pasted/browser-selected image bytes)
- `capture_qr() -> QrResult` (hide the main window, select a rectangle over a frozen in-memory desktop snapshot, then decode locally; no clipboard or disk round-trip)
- `copy_text({ text: string }) -> void`
- `get_preferences() -> Preferences`
- `update_preferences({ shortcut: string }) -> Preferences`
- `preview_renames({ paths: string[] }) -> RenameItem[]`
- `apply_renames({ items: RenameEdit[] }) -> RenameOutcome`
- `undo_rename() -> RenameOutcome`
- `rename_history() -> HistorySummary | null`
- `search_tmdb({ query: string, kind: 'movie'|'tv' }) -> TmdbMatch[]` (public TMDb search page, no API credential)
- `list_resource_sites() -> ResourceSite[]`
- `save_resource_site({ id: string|null, name: string, url: string }) -> ResourceSite[]`
- `delete_resource_site({ id: string }) -> ResourceSite[]`
- `open_resource_site({ id: string }) -> void`
- `resource_browser_state() -> ResourceBrowserState` (bound local toolbar only)
- `resource_browser_action({ action: 'back'|'forward'|'reload'|'stop'|'home'|'navigate', url?: string }) -> void` (bound local toolbar only)
- `capture_frontend_ready() -> boolean` (main window only; acknowledges listener readiness and consumes one queued capture request)

Types (all serialized field names camelCase):

```ts
interface QrResult { texts: string[]; imageDataUrl: string }
interface Preferences { shortcut: string; shortcutAvailable: boolean; coldStartConfigured: boolean; coldStartError: string | null }
interface ResourceSite { id: string; name: string; url: string }
interface RenameItem { id: string; sourcePath: string; originalName: string; suggestedName: string; title: string; year: string | null; extension: string; kind: 'movie'|'tv'; confidence: 'high'|'review'; notes: string[]; isDirectory: boolean; groupId: string | null; episode: string | null }
interface RenameEdit { id: string; sourcePath: string; targetName: string }
interface RenameOutcome { count: number; message: string }
interface HistorySummary { count: number; createdAt: string }
interface TmdbMatch { id: number; title: string; originalTitle: string; year: string | null; overview: string; kind: 'movie'|'tv' }
```

`id` is opaque backend authorization token associated with previewed path; backend never accepts unpreviewed arbitrary operations. Backend preserves all video extensions and the directory hierarchy. Selected directories are scanned for video files; nested name changes are previewed explicitly, children execute before parent folders, and undo proceeds in reverse order. Directory identity uses Windows volume/file IDs, with compatibility for legacy journals. Failed parent restoration blocks descendant operations. Preview registers sources. Execution enforces non-collision, no overwrite, valid Windows names, source consistency, and persistent undo journal.

Rust renamer module: expose serializable types above and `pub struct RenameEngine`; `RenameEngine::new(data_dir: PathBuf) -> Self`; methods `preview(&mut self, paths: Vec<String>) -> Result<Vec<RenameItem>, String>`, `apply(&mut self, items: Vec<RenameEdit>) -> Result<RenameOutcome,String>`, `undo(&mut self) -> Result<RenameOutcome,String>`, `history(&self) -> Result<Option<HistorySummary>,String>`. Parent wraps Mutex engine in Tauri state and commands. Module can use serde, serde_json, regex, uuid (v4), chrono, tempfile (dev). Keep journals recoverable, partial failure honest.

Rust qr module: async Tauri `#[tauri::command] pub async fn decode_clipboard()`, `decode_image(data: Vec<u8>)`, `capture_qr(window: tauri::WebviewWindow)` and sync `copy_text(text: String)`. Helpers should unit test decoding. Dependencies parent includes: image 0.25 (png,jpeg,gif,bmp,webp only), rqrr 0.10, arboard 3, base64 0.22, tauri 2, windows-sys 0.61 (Win32_UI_Shell, Win32_UI_WindowsAndMessaging, Win32_Foundation). Commands return Result<QrResult,String>. Coordinate dependency changes with parent.

Desktop capture contract: `capture_qr` keeps its frontend/Tauri interface unchanged. It temporarily hides the main window, obtains a frozen desktop image in memory, and lets the user select a rectangle from that image; Escape, right-click, focus loss, or timeout cancels and restores the main window. Decode the selected pixels locally. This path must not read from or write to the system clipboard and must not persist the screenshot. The separate paste-image flow continues to read images explicitly pasted by the user, and the desktop Copy button remains the only way to put a decoded QR text on the clipboard. Do not invoke Windows Snipping Tool or poll the clipboard for capture completion. The former bare `ms-screenclip:` launcher is deprecated; the current Snipping Tool URI requires MSIX packaging, while this app ships unpackaged NSIS. See [Windows screen snipping launch guidance](https://learn.microsoft.com/en-us/windows/apps/develop/launch/launch-screen-snipping) and [Snipping Tool URI guidance](https://learn.microsoft.com/en-us/windows/apps/develop/launch/launch-snipping-tool). Native selection implementation details and platform limitations must be confirmed against the implementation before documenting them as guarantees.

Frontend file ownership: src/App.tsx, src/styles.css, src/types.ts. Parent owns src/main.tsx, config and backend other than qr.rs/rename.rs. Use lucide-react, @tauri-apps/api, @tauri-apps/plugin-dialog. File picker open({multiple:true,directory:false,filters:[...]}) for movie; directory:true for folders. Tauri native onDragDropEvent for path drops. Browser preview allowed but show desktop-only limitation honestly; can provide clearly labeled examples. Do not invoke real filesystem from browser fallback. Accept image drops via DOM, native path drops may need read through QR command (coordinate). QR input hidden type=file bytes.

Style revised in 0.1.8: a compact Apple-inspired pearl surface, floating pill selection, rounded controls, subtle elevation and visible keyboard focus, native Windows title bar, and an internally scrolling original/new-name table. QR and rename share the default 520×240 window with minimum 480×220. Mode/content changes never resize the window; workspace content scrolls inside the user-sized window. Both modes use the same fixed-grid empty-state component, identical action widths/order and fixed footer height. Stable scrollbar gutters prevent horizontal shifts; result actions and summary/card origins align between modes. Resource shortcuts use neutral solid-gray surfaces with no positional hover transform. Only QR and rename are tabs. Resource links are two compact toolbar shortcuts, with URL-only editing in an anchored viewport-bounded popover; additional existing sites remain reachable in a compact menu. No independent resource page, automatic copy, settings page, or About UI. The screenshot shortcut editor is inline at the bottom. TMDb attribution is inline in the search panel.

Selection has no movie/TV switch. Movie containers emit individual video rows without renaming the container. TV folders and episode files share a preview-scoped groupId. Selecting a TMDb match or editing the TV folder name updates sibling episode suggestions. A season folder chosen alone never authorizes renaming its ancestor. Unknown episode names remain unchanged. Subtitles and directory structure remain untouched. Directory scan limit: 8 levels, 5000 videos, links/reparse points rejected. A global shortcut (default Alt+Q) starts screen capture; there is no capture button. Saved preferences contain only the shortcut, and legacy autoCopy keys are ignored.

Resource sites: list starts empty; names (1–80 characters), canonical HTTP(S) URLs and UUIDs persist in resource-sites.json using atomic replacement. Corrupt stores are reported and never silently replaced. Reject credentials, controls, malformed schemes, loopback/unspecified IPs (including mapped IPv6), localhost and *.localhost. Each site uses a stable resource-<UUID> window with its own persistent WebView2 data directory. Reopening focuses the existing page; editing closes its old window after persistence, so the next click opens the changed address. Safe popup links navigate the existing window; all new windows and downloads are denied. Navigation repeats URL validation. Deleting a bookmark closes its window but retains its browser profile.

The native resource window is created and shown before its child WebView2 is created asynchronously. Hold the window-label reservation until attachment/cleanup finishes; closing, editing or deleting during startup must cancel the old attachment. Keep the per-site persistent profile, navigation checks, and permission boundary intact. The resource window has a 56 px trusted local toolbar above the isolated remote WebView. Toolbar actions are back, forward, reload, stop, home (the saved favorite URL), and HTTP(S) navigation. Shortcuts: Alt+Left/Right for back/forward, Ctrl+L for the address bar, Ctrl+R and F5 for reload, Esc to stop; while the address bar is focused, Esc restores the current page URL. Address navigation is submitted only on Enter. Native WebView2 history and source updates must synchronize toolbar state for ordinary and SPA navigation. `resource_browser_state() -> { url, title, loading, canGoBack, canGoForward }` reports state, and `resource_browser_action({ action: 'back'|'forward'|'reload'|'stop'|'home'|'navigate', url?: string }) -> void` performs actions. Both commands are callable only by the toolbar webview strictly bound to the expected parent window, resource UUID, and exact local toolbar URL. The remote page receives no command permission, and toolbar webviews are denied all other local commands. Grant only `listen`/`unlisten` to the explicitly named toolbar webviews; do not grant capabilities to the resource window as a whole. The existing trusted-main-only invoke rule must be narrowly extended for these two toolbar commands and continue rejecting every other non-main invocation. This reduces the delay before visible feedback; it does not accelerate the remote website's network requests. Measurements and their limits belong in VALIDATION.md.

Chrome extension: `extension/manifest.json` is an independent Manifest V3 product with minimum Chrome 116. Build output is `dist-extension`; Chrome developer mode must load that generated directory, not the TypeScript source directory. `npm run package:extension` creates `artifacts/Reelink-Chrome-<package version>.zip`, currently 0.2.2; the build rejects mismatched manifest/package versions. This release's Chrome workflow change is version metadata only. The `capture-qr` command defaults to Alt+Q. It captures only the active tab's visible viewport, draws a frozen selection overlay, crops locally in the offscreen document, and decodes with bundled jsQR. One result is copied automatically; each result among multiple results has its own Copy button. The result session remains available for another selection or copy. Screenshot state is cleared when the selection page closes, on Esc, on source-page navigation, or after the 120-second session expiry. Restricted pages that cannot host the overlay use the extension's capture page. `file://` access depends on the user's Chrome extension setting.

The extension requests only `activeTab`, `scripting`, `offscreen`, `clipboardWrite`, and `storage`; it has no host permissions. `storage.session` holds temporary session metadata and decoded results, never the screenshot; frozen screenshot and preview are held in extension session memory by the selection UI and offscreen document, and are not written to disk. The extension has no remote connection permission, and its extension-page CSP sets `connect-src 'none'`. It does not invoke Reelink/Tauri commands and includes no rename or resource-favorites feature. The desktop app's QR flow remains separate: it decodes locally and copies only after the user clicks Copy.

Cold-start capture: the installed build's current-user Start Menu shortcut `Reelink 截图.lnk` targets the current `reelink.exe` with exactly `--capture`; the ordinary Desktop `Reelink.lnk` remains a normal launch. The shortcut starts the app if it is closed. If another instance is already running, the single-instance handler forwards the capture request to that main instance. The main frontend registers its capture listener before calling `capture_frontend_ready`; requests received before readiness coalesce into one pending request, and a request received while capture is active is dropped. No resident helper, startup entry, or network service is added. The installer and uninstaller use `--install-capture-shortcut` and `--remove-capture-shortcut` CLI modes, which load no GUI. They update or remove only a local, regular shortcut whose target is the exact current executable and whose arguments equal `--capture`; links with a different target/arguments, invalid content, or a reparse point are refused and preserved. Uninstall removes the owned shortcut but does not delete user data. Shortcut bytes are serialized with `IPersistStream` in memory, verified, and atomically committed. The program then dirties the hotkey in memory and requests registration through `IPersistFile::Save` on the final `.lnk` path only; this final native save may rewrite the file and is not atomic. Previous owned bytes are backed up until save and readback succeed. On failure, restoration is attempted only when the current bytes still match the committed bytes under an exclusive, non-reparse file handle; otherwise the current file and recovery backup are retained with an error. Staging filenames are never passed to `IPersistFile::Save`. Shell notifications refer only to the final shortcut. File-format tests and registration return values do not prove physical hotkey activation.

Windows launches use the GUI subsystem in both release and debug builds, so opening a QA executable from Explorer does not create a console window. A subclass installed on the main window's owning UI thread consumes `WM_SYSCOMMAND/SC_HOTKEY` and queues capture without the default foreground activation; all other messages retain their default processing. The subclass releases its context on window destruction and prevents Rust unwinding across its native callback. When the installation owns its Shell shortcut and saved preferences were read successfully, startup explicitly associates the saved hotkey with the main window, including ordinary launches with no Shell-provided association. After the shortcut file and preferences are saved, that association is synchronized again. Unknown ownership or unreadable preferences must not create a binding from fallback defaults; portable builds retain their in-process registration. A same-value retry still checks the native result, including result 2 (another window has the same hotkey), and a failure is reported without claiming full synchronization. [Window hotkey semantics](https://learn.microsoft.com/en-us/windows/win32/inputdev/wm-sethotkey) differ from `RegisterHotKey`; neither a busy/free probe nor source tests prove the cold/warm physical workflow.

Debug builds can opt into `REELINK_QA_SHORTCUT_TRACE=1` to print capture CLI arguments, the executable path and the shortcut's resolved physical path/ownership to stderr. This diagnostic is silent by default and excluded from release builds. In packaged development tools, a logical Roaming path can still resolve into the tool's LocalCache even when the launched process reports no package identity; installation validation must inspect the actual file handle path. Resolve that path for each run rather than carrying forward an earlier unredirected observation.

On installed builds with an owned capture shortcut, changing the inline shortcut updates both the link and saved preferences; failure attempts to restore the prior shortcut file and reports incomplete recovery through `coldStartError`. Portable/development builds without an owned link continue to use the in-process Tauri global shortcut and do not create a system link automatically. `Preferences.shortcutAvailable` reports only whether runtime registration succeeded. `coldStartConfigured` reports that the system shortcut configuration is saved; it does not prove the hotkey is globally conflict-free or that Explorer will activate it. An owned or unreadable link stays in system mode when synchronization fails; it never silently falls back to in-process registration. `coldStartError` reports the failure in the inline shortcut editor, and a later save retries synchronization. Unreadable preferences are preserved and cannot be overwritten from fallback defaults. In cold-start mode the footer labels the action “启动截图”; if the hotkey conflicts, the user must choose another combination. These startup and installed-shell behaviors require actual Windows desktop verification; they are not established by source-level checks.

Relevant Chrome API constraints: [activeTab](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab), [commands](https://developer.chrome.com/docs/extensions/reference/api/commands), [offscreen documents](https://developer.chrome.com/docs/extensions/reference/api/offscreen), and [storage](https://developer.chrome.com/docs/extensions/reference/api/storage).

Security boundary: capabilities/default.json grants local application permissions only to the main window. capabilities/resource-toolbar.json grants only event `listen`/`unlisten` to local toolbar webviews, with no remote capability. The two browser commands are enforced by the centralized invoke handler using strict parent-window, resource UUID, and exact local toolbar URL binding. Tauri 2.11.6 webview/mod.rs explicitly checks ACL for every remote request, including custom app commands without an app ACL manifest. Every command except the two toolbar browser commands is rejected for non-main webviews. Resource windows cannot navigate to app/custom protocol origins; on-page-load focus is restricted to main. Main-window operations remain available while browsing. These boundaries require desktop WebView2 verification in addition to URL and persistence unit tests.
